# Вшивание ядра `gemm_fp16 / sm_70` в inference

Инструкция для ХОСТ-дерева (движка вывода). Боевое дерево этого проекта
(`$TEMPO_HOST_TREE`) здесь **только читается**;
изменения делает владелец хост-дерева по этой инструкции.

---

## 0. Что вы получаете и чего НЕ получаете

**Получаете:** плотное умножение `C = A*B^T` в половинной точности с одинарным накопителем,
исходником, под sm_70, с диспетчером по полосе `M` и обязательным откатом.
Замеренные числа — в `report.md` (три числа: против входа, против соперника, доля в стене).

**НЕ получаете:**
* покрытия всех форм — предикат узкий намеренно (см. §3), непокрытое уходит в откат;
* эпилогов (слияние `silu(gate)*up` не сделано; цена названа: ~6 % одного матмуля);
* превосходства над сильной библиотекой в глубоком префилле — там 0.77..0.91,
  и причина названа честно (расписание, которое продукт не эмитит).

**Ставьте это ядро, если вам нужен СТЫК**, а не только маржа: как только умножение ваше,
между слоями можно везти не только активацию (замерено: при `M<=64` промежуток между
матрицами — 0.6 % трафика против весов), и открывается класс ходов, которого нет,
пока формат стыка диктует чужая библиотека.

## 1. Файлы поставки и кто за что отвечает

| файл | роль | кто правит |
|---|---|---|
| `kernel.cuh` | `__global__` + весь device-код в `namespace tempo::gen` | НИКТО (порождается) |
| `launch.cuh` | POD `GemmParams` + `applicable()` + ОБЪЯВЛЕНИЕ `launch()`; **ни одного типа фреймворка** | НИКТО |
| `launch.cu` | **ОПРЕДЕЛЕНИЕ** `launch()`: единственная единица трансляции, где инстанцируются ядра. **СОБИРАТЬ ОБЯЗАТЕЛЬНО** | НИКТО |
| `dispatch.inc` | таблица `(M,N,K) -> инстанциация` + `TEMPO_FALLBACK` | порождается `gen_dispatch.py` из `select.py` |
| `ship_probe.cu` | фальсификатор ПОСТАВЛЯЕМОГО пути: собирается только из файлов выше, сверяет значения | НИКТО |
| `select.py` | тот же предикат на python: зовётся ОДИН раз при загрузке | владелец поставки |
| `gen_dispatch.py` | порождение `dispatch.inc` — один источник, два потребителя | владелец поставки |
| `manifest.json` | паспорт: предикат, регистры/разлив/кадр/smem, обе планки, карта, частоты, соседи, хэш исходника | порождается |
| `report.md` | ТРИ числа, включая долю в стене | порождается |
| `LICENSE` | копия TRL рядом с кодом (п. 2.2 требует сохранения при копировании) | — |

Файла `bind.cpp` в поставке НЕТ, и это осознанно: связывание с фреймворком — единственное
место, где нужен код хост-дерева, и оно пишется под конкретный фреймворк (см. §2, шаблон).

## 2. Как подключить (пять шагов, порядок обязателен)

### Шаг 1. Сборка — только из исходника, каталог сборки задаётся ЯВНО

```bash
export TEMPO_BUILD_DIR="${TEMPO_BUILD_DIR:?set an explicit build directory}"  # НИКОГДА не наследовать
mkdir -p "$TEMPO_BUILD_DIR"

# В СПИСОК ИСТОЧНИКОВ ХОСТ-ДЕРЕВА ОБЯЗАТЕЛЬНО ВХОДИТ launch.cu.
# Без него `tempo::gen::launch` объявлен и НЕ ОПРЕДЕЛЁН -- ошибка КОМПОНОВКИ, а не работа.
nvcc -O3 -std=c++17 -arch=sm_70 -c launch.cu -o "$TEMPO_BUILD_DIR/tempo_launch.o"
```

**Проверьте поставку до связывания** (нужна карта; свободная — нет, сверяются значения):

```bash
python3 test_gate.py --with-card          # соберёт ship_probe.cu + launch.cu и ЗАПУСТИТ
# ожидаемо: ИТОГ ПОСТАВЛЯЕМОГО ПУТИ: PASS 6 / FAIL 0
```

Причины замеренные:
* хост-дерево всё равно собирает расширения из исходника — заранее собранный `.so`
  прибивает ABI (компилятор + стандартная библиотека + версия фреймворка);
* **один прогон под `sudo` делает каталог сборки собственностью root**, и после этого падает
  ВСЁ с ошибкой доступа, а харнесс рапортует десятки провалов, не имеющих отношения к правке.
  Читайте ПЕРВУЮ строку трассы;
* перед сборкой снесите застарелый файл блокировки JIT: убитый процесс оставляет `lock`,
  который блокирует каждый последующий подъём НАВСЕГДА и БЕЗ трассы.

### Шаг 2. Связывание (пишется в хост-дереве, шаблон)

```cpp
// bind.cpp -- ЕДИНСТВЕННОЕ место, знающее про фреймворк
#include "launch.cuh"

// tensor -> POD -> launch. Ни одного типа фреймворка ниже этой функции.
static void gemm_fp16(const void* A, const void* B, void* C,
                      int M, int N, int K, void* stream) {
  tempo::gen::GemmParams p{
      static_cast<const __half*>(A), static_cast<const __half*>(B),
      static_cast<__half*>(C), M, N, K, K, K, N};
  if (!tempo::gen::applicable(p)) { /* TEMPO_FALLBACK: штатный путь */ return; }
  auto rc = tempo::gen::launch(p, static_cast<cudaStream_t>(stream));
  if (rc != cudaSuccess) { /* TEMPO_FALLBACK */ }
}
```

### Шаг 3. Вентиль — по умолчанию ВЫКЛЮЧЕН, плюс гейт по форме

```python
TEMPO_KERNELS = os.environ.get("TEMPO_KERNELS", "0") == "1"   # умолчание 0
```

Ровно так устроено отгруженное ядро внимания этого проекта: флаг окружения плюс гейт
по форме. Ядро, включённое по умолчанию, однажды ломает чужой сервер, и виноват будет продукт.

### Шаг 4. `entry_proof` — ОБЯЗАТЕЛЕН, до всякого замера

Докажите, что в ядро **заходят**. Два законных способа:
* счётчик маршрута из воркера (инкремент в нашей ветке, печать при завершении);
* побитовый диф выхода с выключённым ядром на одной и той же форме.

**Правило проекта, оплаченное днём работы:** A/B, сдвинувший сквозную метрику на 0.03 %,
означает, что туда НЕ ЗАХОДИЛИ. В этом проекте так обнаружилось, что 42 слоя из 48
шли мимо наших ядер, а «улучшение» было шумом.

### Шаг 5. Гейт корректности — РАНЬШЕ секундомера

```bash
python3 kernels/shipped/gemm_fp16/sm_70/test_gate.py --host-tree /путь/к/хост-дереву
```

Гейт воспроизводится **в хост-дереве**, а не только у нас: «прошло у нас» не равно
«пройдёт у них» (другой компилятор, другая версия фреймворка, другой каталог сборки).

## 3. Предикат применимости (что покрыто и что нет)

Покрыто:
* `dtype`: половинная точность на входе и выходе, **одинарный накопитель**;
* раскладка: `C = A*B^T`, оба операнда k-мажорные, плотные (шаги равны `K`, `K`, `N`);
* выравнивание 16 байт у всех трёх указателей;
* `N % BN == 0` и `K % BK == 0` для выбранной строки лестницы.

Не покрыто и уходит в откат:
* любая форма, где `N` не делится на 128/256, а `K` — на 32/64;
* транспонированные и страйдованные раскладки;
* пакетное умножение, split-K, эпилоги;
* `M > 256` при узком `N`, не кратном 128.

**Потолок K по накопителю.** Одинарный накопитель точен, пока `|сумма| < 2**24`. На данных
с нулевым средним это выполняется до очень больших `K`, но на ОДНОСТОРОННЕМ входе (после
неотрицательной нелинейности) сумма растёт линейно, а не корнем. Если ваш вход односторонний
— сверяйте с эталоном ПОВЫШЕННОЙ точности на своей форме, а не доверяйте нашей таблице.

**Ловушка эталона:** штатное умножение в половинной точности ВОЗВРАЩАЕТ половинную и
переполняет ВЫХОД при исправном одинарном накопителе. Сверка «штатным» путём даёт
ЛОЖНЫЙ ОТРИЦАТЕЛЬНЫЙ. Эталон — только в одинарной точности и выше.

## 4. Приватный формат на стыке (если пойдёте дальше маржи)

Приватный формат между вашими же звеньями законен, **пока все читатели ваши**. Но гейты у
склада и у ядра — РАЗНЫЕ, и это уже стоило проекту аварии: 40 слоёв из 48 читали данные
одного байтового формата как другой и получали мусор. Отсюда отдельный признак
`allow_private_format` в манифесте: ядро обязано ПРОВЕРЯТЬ его, а не предполагать.

## 5. Что мерить после вшивания (и в каком порядке)

1. `entry_proof` — заходят ли (шаг 4). Без него всё дальнейшее бессмысленно.
2. Гейт корректности на ВАШИХ формах (шаг 5).
3. **Доля работы этого умножения в вашей стене.** Считайте её ДО того, как радоваться:
   в этом проекте ядро дало x1.36 изолированно и **0.6 % сквозняком**, потому что его работа
   составляла 16.3 % стены. Счётчик стоит одного прогона, встраивание — дня.
4. И только теперь — сквозной замер парными отношениями с чередованием ВНУТРИ раунда,
   медианой ОТНОШЕНИЙ, закреплёнными частотами и подсчётом чужих процессов до и после.

---

## 6. Откат и снятие

`TEMPO_KERNELS=0` возвращает штатный путь целиком, без пересборки. Любая форма вне предиката
уходит в откат независимо от вентиля. Если ядро отключено, а поведение изменилось — значит
изменилось что-то ещё, и это отдельный дефект.
