# Требования к ВХОДУ темполятора

Вход играет **три** роли, и их нельзя путать:
1. источник спецификации — блок `TEMPO-OP` внутри самого исходника;
2. **эталон значений** для гейта корректности;
3. **знаменатель** метрики «во сколько раз выход обгоняет вход».

## Обязательное

* **Блок `TEMPO-OP` внутри `.cu`.** Не рядом, не в отдельном описании: описание рядом
  неминуемо разъедется с кодом. `recognize` читает блок И СВЕРЯЕТ объявленную точку входа
  и число аргументов с текстом. Не сошлось — **отказ**, а не догадка.
* **Ноль внешних зависимостей.** Только заголовки среды исполнения. Вход обязан собираться
  одной командой и запускаться отдельно.
* **Функция запуска в одну строку** (`*_launch`), чтобы харнесс вызывал РОВНО то же, что и
  отдельная сборка. Иначе меряется не то, что собрано.

## Что во входе НЕ должно быть

Вход пишет человек, **знающий алгоритм и не знающий машины**. Поэтому: ни плиток в
разделяемой памяти, ни двойной буферизации, ни тензорных инструкций, ни векторных загрузок,
ни дополнения строк, ни переупорядочения блоков, ни разбиения по глубине свёртки.
Есть ровно определение операции.

## Единственное исключение — ТОЧНОСТЬ НАКОПИТЕЛЯ

Накопитель в наивном входе — **одинарной** точности, а не половинной. Это **не оптимизация,
а корректность**: при большой глубине свёртки накопление в половинной точности теряет
значащие разряды и даёт другой ответ. Половинный накопитель во входе означал бы сравнение со
**сломанным** входом, то есть завышение выигрыша.

## Почему метрика «против входа» ничего не стоит в одиночку

Наивный исходник идёт на **доли процента** пика. Обогнать его в сто раз не значит ничего, и
поэтому отчёт **не собирается**, если вторая планка не названа. См. `docs/NOT_YET.md` п. 2.
